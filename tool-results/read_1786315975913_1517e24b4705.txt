    50→# 1. PRODUCT DEFINITION
    51→
    52→Royal Palace Health Care Digital Platform is a managed healthcare ecosystem connecting:
    53→
    54→* Patients.
    55→* Doctors.
    56→* Dentists.
    57→* Pharmacies.
    58→* Laboratories.
    59→* Diagnostic centres.
    60→* Logistics personnel.
    61→* Platform administrators.
    62→
    63→The platform is not simply a doctor-directory website or a telemedicine application.
    64→
    65→Its primary differentiator is **continuity of care**.
    66→
    67→The patient journey connects:
    68→
    69→```text
    70→Healthcare Need
    71→      ↓
    72→Provider Discovery
    73→      ↓
    74→Appointment Booking
    75→      ↓
    76→Payment
    77→      ↓
    78→Consultation
    79→      ↓
    80→Structured Clinical Record
    81→      ↓
    82→Prescription / Laboratory Request / Referral
    83→      ↓
    84→Pharmacy / Laboratory / Receiving Provider
    85→      ↓
    86→Result / Fulfilment / Additional Care
    87→      ↓
    88→Follow-Up
    89→      ↓
    90→Continuous Patient Health Record
    91→```
    92→
    93→Everything implemented in the prototype must support this connected journey.

   135→POST /laboratoryRequests

   145→
   146→Treat JSON Server as if it were the real backend API.
   147→
   148→Do NOT tightly couple components directly to `db.json`.
   149→
   150→Never import `db.json` directly into React components.
   151→
   152→Use this architecture:
   153→
   154→```text
   155→React UI
   156→   ↓
   157→Hooks / Feature Logic
   158→   ↓
   159→Service Layer
   160→   ↓
   161→API Client
   162→   ↓
   163→JSON Server REST API
   164→```
   165→
   166→Later:
   167→
   168→```text
   169→React UI
   170→   ↓
   171→Hooks / Feature Logic
   172→   ↓
   173→Service Layer
   174→   ↓
   175→Production REST API
   176→```
   177→
   178→The UI must therefore remain reusable when the backend is replaced.

# Increment 06 checkpoint — public organization discovery

## Status

Increment 06 remains **in progress**. The hospital, pharmacy, and laboratory portion is
implemented and validated. Provider discovery and generated-client adoption remain open;
this document is an implementation checkpoint, not the Increment 06 completion report.

## Implemented architecture

The production PostgreSQL model now separates an organization's legal record from its
public profile, facility locations, governed service taxonomy, organization-level
offerings, and facility-specific availability. Composite foreign keys prevent a facility
from advertising another organization's offering. Database checks enforce publication
timestamps, verification timestamps, normalized slugs/codes, coordinate pairs and
ranges, version values, and nonblank location data. A partial unique index permits one
primary facility per organization. A follow-up global-address migration replaces the
single-market `city/state` assumption with optional locality, administrative-area,
postal-code, address-line, country-code, and coordinate facts. PostgreSQL `pg_trgm` GIN
indexes back the case-insensitive name, summary, address, service-name, locality, and
administrative-area search patterns; ordered B-tree indexes continue to support stable
catalogue pagination.

The API is a capability-owned Nest module with domain ports, an application service, a
Prisma adapter, and presentation validation. It exposes bounded hospital, pharmacy,
laboratory, detail, and type-scoped service endpoints. All list queries use stable
`displayName + id` cursor ordering; cursors are canonical, versioned, filter/type-bound,
and validate their database identifier before use. Repository projections never select
legal names, verification internals, audit facts, memberships, or other private records.
Only active, verified organizations with a published profile, public active facility,
and active facility-specific service availability are discoverable.

The Next.js BFF exposes only explicit public discovery routes in protected environments;
the dynamic allowlist accepts UUID-shaped detail routes rather than broad prefixes. The
patient hospital, pharmacy, and laboratory screens now use the typed public service
boundary with debounced server-side search/location filters, type-scoped service
filters, cursor pagination, request cancellation, loading/empty/retry/server-failure
states, and accessible live status text. Prototype bulk reads and browser-side filtering
are no longer used by these screens.

## Validation evidence

- Clean install, prior-schema upgrade, transactional repair, and database constraints
  passed on disposable PostgreSQL 18 databases; CI repeats this on PostgreSQL 17.6.
- Synthetic seed executed twice without duplication. Schema drift was zero.
- Real-repository verification covered service and location filtering for hospitals,
  pharmacies, and laboratories, stable pagination, private-field exclusion, and a fixed
  five-query list shape independent of page size (no N+1 behavior).
- Representative plans used `organizations_public_discovery_idx`,
  `organization_services_service_status_org_idx`, and the public discovery trigram
  indexes. The ordinary B-tree plans use the natural PostgreSQL planner choice. The
  trigram checks disable sequential and ordered B-tree scans for their individual
  statements to prove `ILIKE` operator/index eligibility because those alternatives are
  legitimately cheaper at the small fixture size; they are not presented as the natural
  small-fixture plan. Exact observations are regenerated by the query-plan gate and are
  not production latency promises.
- API tests: 133 passed. Web tests: 29 passed. Zero-warning lint, strict type checks,
  all seven production package builds, 53 Next.js routes, standalone packaging, both
  Prisma schema validations, and the high-severity dependency audit passed.

## Deliberately open work

Provider discovery must not be represented as an organization or copied from the
prototype's flat provider record. Before its durable model is approved, product and
clinical owners must decide whether independent providers are allowed, how providers
affiliate with organizations/facilities, which specialty taxonomy is authoritative,
which credential facts may be public, and whether languages, consultation modes, fees,
availability, and ratings belong in the first public projection. The existing clinical
terminology and qualified clinical/privacy approval gate therefore applies.

The controlling plan also requires a generated frontend client. This checkpoint uses
the workspace's strongly typed shared contracts and centralized HTTP service layer, but
does not mislabel that hand-written boundary as generated. Increment 06 cannot be marked
complete until the repository establishes and adopts its API description/code-generation
pipeline or the controlling plan is explicitly amended.

## Standards review

The implementation is capability-scoped, readable, normalized, constraint-backed,
query-bounded, public-projection-only, exact-route allowlisted, and reusable across three
organization types. It adds no country, currency, provider, cloud, identity-vendor,
payment, or clinical-terminology default. Synthetic catalogue and location values are
explicitly non-production data and now exercise multiple countries.
No broad generic CRUD endpoint, client-side authorization, N+1 query, unpublished-data
fallback, hard-coded production credential, or silent plan deviation was introduced.

# MASTER BUILD PROMPT — ROYAL PALACE HEALTH CARE CLICKABLE MVP PROTOTYPE

You are acting as a senior product engineer, React/TypeScript architect, healthcare-platform UX engineer, frontend engineer, API architect, and QA engineer.

Your task is to build a **fully functional, high-fidelity clickable MVP prototype** for:

# Royal Palace Health Care Digital Platform

This is not a collection of static mockup screens.

It must behave like a real application:

* Users can log in.
* Users can switch between demo personas.
* Patients can discover doctors.
* Patients can book consultations.
* Appointments are created in the mock database.
* Doctors can open appointments.
* Doctors can document consultations.
* Doctors can create prescriptions.
* Doctors can request laboratory tests.
* Doctors can create referrals.
* Pharmacies can receive prescriptions.
* Pharmacies can process pharmacy orders.
* Laboratories can receive requests and upload results.
* Logistics users can process deliveries.
* Administrators can verify providers and manage pricing.
* Actions must update `db.json`.
* Changes must appear in the appropriate dashboards.
* Status changes must persist after refreshing the application.

The prototype will use:

* React
* TypeScript
* TSX
* Vite
* React Router
* JSON Server
* `db.json`
* REST-style API requests
* Responsive web design

Use the existing project stack and dependencies when a project already exists. Do not unnecessarily replace existing tooling.

The prototype must be architected so that JSON Server can later be replaced by the actual Royal Palace backend without requiring a major frontend rewrite.

---

# 1. PRODUCT DEFINITION

Royal Palace Health Care Digital Platform is a managed healthcare ecosystem connecting:

* Patients.
* Doctors.
* Dentists.
* Pharmacies.
* Laboratories.
* Diagnostic centres.
* Logistics personnel.
* Platform administrators.

The platform is not simply a doctor-directory website or a telemedicine application.

Its primary differentiator is **continuity of care**.

The patient journey connects:

```text
Healthcare Need
      ↓
Provider Discovery
      ↓
Appointment Booking
      ↓
Payment
      ↓
Consultation
      ↓
Structured Clinical Record
      ↓
Prescription / Laboratory Request / Referral
      ↓
Pharmacy / Laboratory / Receiving Provider
      ↓
Result / Fulfilment / Additional Care
      ↓
Follow-Up
      ↓
Continuous Patient Health Record
```

Everything implemented in the prototype must support this connected journey.

# 2. CRITICAL PROTOTYPE OBJECTIVE

Build a prototype that looks and behaves realistically enough for:

* Client review.
* Stakeholder presentation.
* User-flow validation.
* UX validation.
* Development planning.
* Future conversion into the production application.

The system must therefore contain real application state.

Do not build fake screens where every button simply displays an alert.

Important actions must update data through JSON Server.

Example:

When a patient books an appointment:

```text
POST /appointments
```

The new appointment must then appear in:

* Patient → Appointments.
* Doctor → Appointments.
* Doctor → Dashboard.
* Admin → Appointments.

When the doctor completes the consultation:

```text
PATCH /appointments/:id
POST /clinicalEncounters
POST /prescriptions
POST /laboratoryRequests
```

The information must subsequently appear in the patient's medical records.

This cross-portal behaviour is essential.

---

# 3. PROTOTYPE DEVELOPMENT PRINCIPLE

Treat JSON Server as if it were the real backend API.

Do NOT tightly couple components directly to `db.json`.

Never import `db.json` directly into React components.

Use this architecture:

```text
React UI
   ↓
Hooks / Feature Logic
   ↓
Service Layer
   ↓
API Client
   ↓
JSON Server REST API
```

Later:

```text
React UI
   ↓
Hooks / Feature Logic
   ↓
Service Layer
   ↓
Production REST API
```

The UI must therefore remain reusable when the backend is replaced.
